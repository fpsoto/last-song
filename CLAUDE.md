# CLAUDE.md

## What this is
LAST SONG: a playable 2D arcade beat 'em up proof of concept in plain HTML5 / CSS3 / vanilla JavaScript (Canvas 2D). No frameworks, no build step, no backend, no external assets. Live at https://fpsoto.github.io/last-song/.

## Non-negotiable conventions
- **Everything is in English**: game text, code, comments, issues, PRs, commit messages. Comment the interesting or hard parts of the code.
- Classic `<script defer>` files sharing the global `LS` namespace (no ES modules), so the game also runs from `file://`. Script order lives in `index.html`.
- All art and sound is generated by code. Do not add image or audio files.
- Relative paths only, so the site works under any repository name.
- Combat stays decoupled from rendering (attack defs are data; `game.onHit` raises effects).

## Running and verifying
- Open `index.html`, or serve the folder with any static server.
- `node --check js/*.js` must pass (CI runs it).
- Dev flags (see README): `?debug=1`, `?start=1`, `?skip=N`, `?god=1`, `?auto=1`, `?warp=N`... Use them to reach the part you changed fast.
- No console errors, on the title screen and during play.

## Tracking and git flow
- **Every change starts as a GitHub issue**, opened from the Feature or Bug template (context, scope, acceptance criteria).
- Branch per change, cut from **`develop`**, named `<type>/<issue number>-<short-slug>` where type is `feature`, `bug` or `chore` (for example `feature/12-gamepad-support`). Commits reference the issue (`refs #N`).
- PR into `develop`, using the PR template: first line `Closes #N`, then a `## Summary` of what was implemented and a test plan.
- **A case closes when its PR is merged** (not at release): `.github/workflows/close-linked-issues.yml` closes the referenced issues on merge into `develop` and posts the PR's Summary as the closing comment.
- Every issue is assigned to `fpsoto` and gets a milestone.
- Issue titles are `[Feature] ...`, `[Bug] ...` or `[Chore] ...` followed by a short sentence in sentence case.
- Labels: `feature`, `bug`, `chore`, `documentation`, plus one or more of `area: gameplay`, `area: art`, `area: audio`, `area: infra`, `area: docs`.
- **No AI attribution**: no `Co-Authored-By` trailer and no "Generated with..." line in commits or PRs.

## Versions and releases
- Semver. `0.x` = pre-production (anything may still change); **`1.0.0` = a finished, balanced, playtested stage**. One milestone per version (`v0.1.0`, `v0.2.0`, ..., `v1.0.0`).
- **A release is a branch, never a hand-made tag**: cut `release/X.Y.Z` from `develop` (its name is the single source of the version) and open a PR `release/X.Y.Z` -> `main`. Merge with **Create a merge commit**. Then:
  - `.github/workflows/release.yml` creates the GitHub Release and its `vX.Y.Z` tag (pre-release for 0.x) and opens the back-merge PR `main` -> `develop` (merge it with a merge commit too).
  - `.github/workflows/pages.yml` redeploys the site, because `main` changed.
- Afterwards close the version's milestone. Keep the `release/X.Y.Z` branch as the record of the release.

## Git on this machine
- `git` is not installed here. Changes are pushed with the `gh` REST API (blobs -> tree -> commit -> ref), or from a clone made on a machine that has git.
- `gh` has two accounts; `fpsoto` (personal) must be the active one for this repo.
